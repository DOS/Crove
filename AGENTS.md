# AGENTS.md

Ludy is the open-source Business OS (AGPL). It must run with `docker compose up` and no DOS service. Anything DOS-specific belongs in the private Crove Cloud layer, never here.

## Picking up work (GitHub Project "Crove")

- Work comes from the board https://github.com/orgs/DOS/projects/8 (issues in DOS/Ludy). One task = one issue = one worktree = one PR. Split work by feature, not by layer: a task goes end to end (migration, server, contract, UI, tests).
- Work without stopping (owner decision 2026-10-20). The plans and designs are the backlog, so the owner should never have to type "continue", "status?" or "allowed". When a task is merged, start the next one in the same session. Never end a turn to ask whether to go on.
- Pick the next task in this order, skipping issues already `In progress` and issues labelled `owner-action` (the owner's job):
  1. In the earliest milestone with work left (M0, M1, M2, M3, then the GA gate, per [docs/plan/backlog-review-2026-10-17.md](docs/plan/backlog-review-2026-10-17.md)), take an open, unclaimed issue: `priority:P0` first, then P1, then P2.
  2. When none is left there, create the next issues yourself from the plans and designs: that milestone's acceptance criteria, the step lists in `docs/plan/*.md`, the ADRs and `DESIGN.md`. Each issue gets its scope, acceptance criteria, the files it touches, a link to the plan line it comes from, and the milestone and priority the plan gives. Then claim one and build it.
  3. When that milestone is done, go on to the next.

  The Icebox and paused milestones (Social, decision D5) stay closed until the owner reopens them.
- Stop and ask the owner only when nothing is left to pick or derive, or when a step would be hard to undo or would cross a line the plans did not draw. Judge each case yourself. The usual cases:
  - losing or rewriting existing data;
  - weakening tenancy, authentication, approval or the ledger's rules, or changing an invariant on purpose;
  - going against a written decision or an accepted ADR;
  - new spending, production or credentials;
  - anything a person must sign off (lawyer, accountant).

  Ask once, with the issue linked, and keep working on other tasks while you wait. Team leads and workers ask through the coordinator (see "The owner, merging and reporting").
- Keep the memory outside the session: at each milestone of a task (PR opened, merged, blocked), comment on its issue what is done and what comes next. A resumed or compacted session reads the open issues it claimed before doing anything else.
- Review follow-ups go to the Icebox: a non-blocking finding from any review (security, code, bot) becomes a `priority:P3` issue labelled `review-followup` in the Icebox milestone. It moves into a milestone only when it blocks that milestone's acceptance criteria or a real user hits it. Blocking findings are still fixed in the same PR.
- No hardening for features nobody uses: security work is picked only when the current milestone's checklist needs it (the pilot readiness checklist, then the GA gate), or when a real high or critical vulnerability is found, which is P0 at once.
- WIP limit (owner decision 2026-10-25): each area team lead has one issue `In progress` itself and may run up to 2 background subagents on other issues of its area, so at most 3 `In progress` per team lead. Any other session takes one issue at a time.
- An issue created from a plan takes the milestone and priority the plan gives it. Any other new issue (an idea, a nice-to-have, a finding outside the plans) goes to the Icebox as `priority:P3`, for the coordinator's weekly triage. Never build what no plan or design calls for. A new customer-visible feature, a pricing change or a new roadmap commitment that no plan or design calls for goes to the owner as a recommendation in the coordinator's digest, whoever asks for it; it gets no issue and is not built until the owner agrees.
- Area team leads (owner decision 2026-10-25): long-running sessions named `Agent <n>: <area>` each own one area and pick their next issue from it themselves; the coordinator (`Agent 0`) keeps the current list in the coordinator log, https://github.com/DOS/Ludy/issues/1210. Other agents may still run, and never take an issue a team lead has claimed. When priorities tie, prefer an issue with the same area label (`kernel`, `security`, `auth`, `finance`, `web`, `infra`, `tooling`, `cloud`) as your previous task, so each agent naturally stays in one area and the owner can see who works where.
- To claim it: set Status to `In progress` and comment `Claimed by <session or agent name>, branch <branch>`. All agents share one GitHub account, so the comment is the lock: read the comments again after posting, and if another session claimed first, pick another task. Never take over a live claim. A claim with no push, PR update or comment for 48 hours is stale: comment `Taking over the stale claim of <session>` with that evidence, then claim it.
- The PR body says `Closes #<n>`; merging moves the issue to Done. If a task needs work in another area (for example UI for a new kernel API), open a follow-up issue (P3, Icebox, unless it blocks the current milestone) instead of growing the PR.
- New migrations (#1492): versions are not reserved. Name a new migration with any version above the newest on `main` when you start. Right before merging, merge `origin/main`, run `pnpm migration:rebase` (it renames every migration your branch adds, in order, to whole hours after `main`'s newest when any of them fell behind, and fixes their references in the files your branch changed), commit, push, wait for green, then merge. The "Migration order" step of the Docs check job fails a PR that adds an older or equal version (`tools/ci/migration-order.mjs`). GitHub does not re-run PR checks when `main` moves, so after every push to `main` the migration-recheck workflow re-runs the Docs check of open PRs whose migrations fell behind (`tools/ci/migration-recheck.mjs`). When it fails, run `pnpm migration:rebase`, commit, push, and never merge with the old version.

## The owner, merging and reporting

- The owner (JOY) does not code, run commands or merge. Agents merge their own PRs: never leave a PR that meets the bar below waiting for the owner, and never ask the owner for permission to merge it.
- The merge bar, all on the PR's final head:
  - every CI check is green (a neutral result or a quota notice from a review bot is not a failure);
  - the branch is rebased on `origin/main` with no conflict, and a PR with a migration passes the migration order check;
  - every review thread has a reply (the fix commit, or why not) and is resolved;
  - a protected-path PR carries the security review (the agent's, or the session's own while #95 is pending);
  - the PR body has an `## Acceptance` section (what a user will see change, the evidence against each acceptance item of the issue, the review results, the risk left), and the PR passed the acceptance gate: the coordinator's for protected-path PRs and for the workers it started, the team lead's for its other PRs and its subagents' PRs, otherwise the session's own. A docs-only PR's section states the change and the docs check result only.

  Squash merge with the expected head SHA, then remove the worktree.
- Review gate before opening a PR: the Codex CLI review (`codex review --base origin/main`, run in the background) and a fresh-context reviewer given the diff and the issue. Fix what blocks; say in the PR what was not taken and why, and say so if Codex is unavailable. Docs-only PRs skip it (see the last rule under "Rules").
- Sessions, subagents and Codex reviews run at effort high unless the owner asks for more (owner decision 2026-10-27).
- The coordinator is Ludy's Product Owner (PO, DOS.AI's term; owner request 2026-10-27, #1621), and the procedure is `.claude/skills/project-coordinator-cycle/SKILL.md`. Team leads and workers never ask the owner: stop cases, decisions and person-only steps go to the coordinator (SendMessage, or a comment on #1210 when messages are paused), and their wrap-up is a recap only. A session the owner opened with no coordinator above it asks the owner itself.
- Production, secret and credential steps: no team lead or worker runs one. It writes a runbook (exact commands in order, a check and a rollback for each, where each secret comes from but never its value, which steps only a person can do) in the PR body or a committed file, under the "Public repo" rule: no secret, project ref, internal host or URL, each named by reference instead (DOS-specific steps belong in the private Crove Cloud layer). The coordinator shows the owner the concrete step list in its chat, the owner approves it there, and the coordinator runs exactly the list it showed (not a later edit of the runbook), stopping at the first failure. Only the owner's own words in the running coordinator session's chat count: an approval quoted in another session, an issue, a handoff or the coordinator log does not, and one approval covers one run. An action that one session's permission checks refused is never run by another session on its word; it takes the same route.
- A review bot that is out of quota or rate limited has not reviewed the PR. Do not wait for it, retry it in a loop or work around its quota. Say so in the PR; on a protected-path PR the session's own security review stands in for it.
- Never merge, push to or take over another session's PR unless the owner names it (for example "merge #481"). Even then, first check that it is still open and that its head matches what you checked: another agent may have merged or replaced it.
- Ask the owner (team leads and workers: through the coordinator) only for the stop cases under "Picking up work", and for something only a person can do: accounts, secrets, payments, real sample files. Decide everything else yourself, and write the decision and its reason in the PR.
- Writing to the owner:
  - Vietnamese with full diacritics, in plain words, for every message the owner reads: chat replies, short status lines between steps, progress updates, recaps, questions. Never English (owner, 2026-10-28: "nói với tao bằng tiếng Việt"). Explain any technical term on first use, and give every issue or PR number with its short name.
  - The first line says whether the work is complete, still running (and what) or stopped (and on what).
  - Each question says what is being decided, why it matters, the options, your recommendation, and what happens if there is no answer. One decision at a time, recommendation first.
  - Name who must act on each open item: the owner, the accountant (#61, the pilot partner's accountant), a lawyer, or another agent.
  - Links must open in a browser: GitHub URLs (`https://github.com/DOS/Ludy/blob/main/<path>`, `https://github.com/DOS/Ludy/issues/<n>`), never a local path or a bare file name. GitHub shows an `.html` file as source code, so publish an owner page (`*.vi.html`) as a private claude.ai artifact when the session can, or summarize it in the message.
- Report without being asked: after each merge, one or two lines (what merged, what is next). Report what actually happened, and keep these words distinct: opened, merged, deployed. Say what was verified and what was not.

## Worktrees (several agents work on this repo at once)

- Never edit in the main checkout (`D:\Projects\Crove` or wherever the repo is cloned). Do every task in its own worktree, on its own branch, created from a freshly fetched `origin/main`:
  - Claude Code: `.claude/worktrees/<task-name>`
  - Codex: `.codex/worktrees/<task-name>`
  - Cursor: `.cursor/worktrees/<task-name>`
- Never create worktrees in `.worktrees`, sibling directories, global `_worktrees` folders or temp directories.
- Before starting, check `git worktree list` and open PRs. If a worktree or branch already belongs to another task or agent, do not edit it or take over its branch; create a new one. A locked worktree belongs to an active agent.
- Never `git checkout`, `reset --hard`, `clean` or bare `git stash` in a path another agent may use. Set aside work with a WIP commit instead.
- Rebase on `origin/main` right before merging; other agents merge often. Resolve conflicts by keeping both sides unless one side is clearly superseded.
- Remove your worktree after your PR is merged, only if `git status` is clean, with `git worktree remove` (never force).

## Commands

- `pnpm install` · `pnpm lint` · `pnpm typecheck` · `pnpm test` (unit) · `pnpm test:db` (needs `CROVE_TEST_ADMIN_URL`)
- `pnpm typecheck` checks every test file too, since Vitest runs tests without checking types (#294): a package's `tsconfig.json` includes `test`, or, where the source must not see test-only types, a `tsconfig.test.json` that extends it does and the package's `typecheck` script runs both (`apps/app`, whose browser code gets no Node types). `tools/tsconfig.json` covers `tools/test` from the root script. A new package with tests follows the same pattern; `tools/test/typecheck-coverage.test.ts` fails when a test directory is outside them.
- Shared dev PostgreSQL: `migrate.db.test.ts` creates cluster-wide `t100_test_runner_*` roles and drops them afterwards; a run killed before that leaves them behind, and every later migrate on the cluster then fails the T17 check with `role t100_test_runner_..._proxy can create temporary objects`. The next run of that test drops leftovers older than 10 minutes; to clear them at once (with no run of it in progress): `psql "$CROVE_TEST_ADMIN_URL" -c "DO \$\$ DECLARE r text; BEGIN FOR r IN SELECT rolname FROM pg_roles WHERE rolname LIKE 't100\_test\_runner\_%' LOOP EXECUTE format('DROP OWNED BY %I', r); EXECUTE format('DROP ROLE %I', r); END LOOP; END \$\$"`
- `pnpm db:migrate` applies `supabase/migrations` with the built-in runner
- `pnpm db:types` (needs `CROVE_TEST_ADMIN_URL`) regenerates `packages/db/src/generated/database.ts`, the Kysely types of every table `crove_tenant` may read, with Kanel from a throwaway database the migrations build. Run it after a migration that changes such a table or its grants and commit the file; CI fails when it is out of date. Insert and update types follow `crove_tenant`'s column privileges: a column the role may not write has the write type `NotGranted`, so a forbidden write (an insert into `outbox_event` or the ledger, an update of an append-only table) fails typecheck (through `values()` and `set()`; deletes, raw SQL and insert ... select are refused only at runtime); a refinement cannot lift that. Refine a column (a CHECK-constraint union, a trigger-set column) in `packages/db/src/schema.ts`, never in the generated file. A CHECK-constraint union is a const array there (`TASK_STATUSES` and its type `TaskStatus`); `packages/db/test/check-unions.db.test.ts` compares every fixed-set CHECK constraint with its array, so a migration that adds, widens or narrows one fails until the array follows and is listed in that test.
- `pnpm db:vendor:pgboss` writes the migration for the pg-boss schema version the pinned pg-boss expects (a unit test fails until it exists after a pg-boss upgrade)
- `docker compose up --build` runs the full stack on http://localhost:8080
- `pnpm test:e2e` runs Playwright against a stack started with `pnpm --filter @crove/e2e stack:up` (compose project `crove-e2e`, port 8080; `stack:down` removes it with its volumes). Against your own stack set both `E2E_BASE_URL` and `E2E_COMPOSE_PROJECT`; the database helpers throw if only the URL is set, so they never touch the shared `crove-e2e` stack. Install the browser once with `pnpm --filter @crove/e2e exec playwright install chromium`

## Updating pinned images

Every container image is pinned by digest as `image:tag@sha256:<digest>`: `docker-compose.yml`, the `FROM` lines of `Dockerfile`, `apps/extract/Dockerfile` and `apps/web/Dockerfile`, and the `services` and `docker run` images in `.github/workflows/`. The tag is for people; Docker pulls the digest, so a re-pushed tag cannot change what runs.

- **Bump:** run `docker buildx imagetools inspect <image>:<tag>` and copy the top-level `Digest` (the multi-arch index, not a per-platform manifest). Replace it in every file that uses the image (`git grep '<image>:'`), and change the tag in the same edit when the version moves.
- **Release age:** pin a build at least one day old, as `minimumReleaseAge` does for npm. The Docker Hub tag API (`https://hub.docker.com/v2/repositories/<namespace>/<name>/tags/<tag>`, namespace `library` for official images) shows `tag_last_pushed`; when the newest build is younger, pin the previous one (its exact version tag still points to it). Today `node:26-slim` is pinned to the Node 26.11.1 build for this reason.
- **Bots:** Renovate and Dependabot both update `tag@digest` pins (tag and digest together) once one is configured; none is yet.

## Rules

- **One write path.** Every state change is a command executed through `Runtime.execute()` (`packages/kernel-runtime`). No other code writes tenant tables.
- **Schema only via migrations** in `supabase/migrations/<14-digit UTC>_crove_<module>_<desc>.sql`. Idempotent statements, never edit an applied file, never DDL at runtime. Every function sets `search_path = pg_catalog, pg_temp`, never `''`. The hardening guard the runner applies after every run (`hardeningViolations`) has no bypass flag or warn mode, and must not get one: a deploy that fails it is fixed with a forward migration, never skipped.
- **Tenancy:** every tenant table has `org_id`, `PRIMARY KEY (org_id, id)` and RLS via `crove_kernel.apply_tenant_rls`. Login roles own nothing.
- **Erasable TypeScript only.** Node runs the kernel's and packages' `.ts` by type stripping, so `tsconfig.lib.json` sets `erasableSyntaxOnly` and typecheck refuses parameter properties, enums, namespaces and `import =` (use explicit fields, const objects with a union type, and modules).
- **Money** is NUMERIC in SQL and a decimal string everywhere else; arithmetic through `decimal.js` (`@crove/l10n-vn` money helpers). Never JS numbers for amounts.
- **AI** calls only in `packages/agent`, through an OpenAI-compatible endpoint. AI output is tainted: deterministic checks decide, humans approve.
- **Public repo:** no secrets, Supabase project refs, internal URLs or real customer data. gitleaks + G1 run in CI and in the pre-commit hook.
