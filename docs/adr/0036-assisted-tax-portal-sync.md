# 0036. Assisted purchase-invoice sync from the tax portal

- Status: accepted
- Date: 2026-10-23
- Deciders: owner (JOY), decision of 2026-10-23 on [#325](https://github.com/DOS/Ludy/issues/325) answering O1 to O3 of the spike; the engineering choices below by the Claude Code session that built it
- Builds on: the spike [tax-portal-invoice-sync.md](../research/tax-portal-invoice-sync.md) (design A of section 4, option 2 of section 6), the portal list import of #465, ADR-0025 (credential vault, `external_call`, per-adapter allowlist), ADR-0013 (evidence storage), ADR-0027 (open-source core)
- Issue: [#325](https://github.com/DOS/Ludy/issues/325)

## Context and problem statement

Downloading purchase invoices from hoadondientu.gdt.gov.vn is the step accounting firms most want gone. The portal has no buyer API, every login needs a CAPTCHA, and the spike found no lawful way to automate a login without a person. The owner decided: an assisted sync per period in the open-source core. The accountant starts it for one client and one period, types the client's portal password and solves the portal's CAPTCHA in Crove; Crove then fetches that period's purchase list and the invoice XML the portal has. Crove never stores the password (database, logs, job payloads, audit rows, error messages, traces) and never solves a CAPTCHA by software.

What had to be decided here: where the portal session lives between the login and the fetch, how the fetched data enters Crove, how outbound calls are bounded, who may run it, and whether self-hosters get it by default.

## Decision

1. **Bounded steps in the API, driven by the screen.** Four RPC procedures (`portalSync.captcha`, `login`, `fetchList`, `fetchXml`) each make a bounded number of portal requests in the API process and answer. The screen runs them in order and holds what the server returns in memory. The password is in exactly one request (`login`), passed to the portal and dropped.
2. **Only the portal's session token is kept, sealed, by the browser.** After the login the API seals `{token, expiry, tax code}` with the deployment's credential vault (AES-256-GCM, ADR-0025) under the binding (org, `gdt_einvoice_session`, user and period) and returns the envelope; a session is refused once the org's tax code differs from the one it was opened with. Nothing is stored server side between steps, so nothing has to be discarded: the envelope expires after 20 minutes, the screen drops it when the sync ends or the panel closes, and an envelope of another user, org or period, or a damaged one, does not open. The CAPTCHA key is sealed the same way (`gdt_einvoice_captcha`, 2 minutes). The binding names differ from every channel provider, so a channel credential can never be opened as a portal session or the other way round. Unlike channel credentials, these envelopes are opened by the API that sealed them; they hold a short-lived session, never a password.
3. **One write path for portal rows.** `fetchList` checks the portal's JSON with the same rules as an uploaded Excel list (`normalizePortalInvoices`, then `checkPortalList`), stores the answer as an import file (`application/json`, the evidence of what the portal said, ADR-0013) and files it with `finance.portal_sync.list`, which replaces the period's earlier synced lists (Excel imports stay) and emits `finance.portal_list.import_requested`. The worker's existing job reads the evidence file with the same rules and records the rows with `finance.portal_list.record`, the only command that writes portal rows; the database refuses those rows outside the system context (#506). The JSON is parsed with `JSON.parse` and numbers kept as their text; no parsing library, no file format, so no sandbox round trip (the sandbox, T12, is for PDF, XML, MIME and spreadsheets).
4. **Invoice XML through the upload path.** `fetchXml` downloads up to 5 XML files per request for invoices the list names, the portal has an XML for (processing state 5) and the reconciliation reports missing from Crove, at most 300 per synced list. Each is stored and recorded as an upload by the accountant (`kernel.file.ingest`, deduplicated by content hash): the worker opens the portal's ZIP in the sandbox and the invoice reaches the Inbox like any upload, with the accountant counted as its author for approval (P10).
5. **Every portal call in the ledger.** Each call is recorded in `crove_kernel.external_call` before it is made and closed after (`finance.portal_sync.call` and `call_end`, target `gdt_einvoice`, steps `captcha`, `login`, `list`, `xml`): who, which step, the outcome class (`WRONG_CAPTCHA`, `WRONG_PASSWORD`, `RATE_LIMITED`, `BLOCKED`, ...), never a password, a CAPTCHA answer, a token or a response body. An XML download is keyed by list and invoice, so it is made once per synced list.
6. **Never lock the client's account.** No login is retried by software. The guard fails closed: every login since the client's last successful one (within a day) that did not succeed counts, unless the portal clearly refused only the CAPTCHA; a wrong password, a locked account, an answer Crove could not read, an outage and a login left unfinished all count, and a refusal that names the password counts as a wrong password even when it also asks for a new CAPTCHA. After 3 the login step is refused before the portal sees it (`PORTAL_PASSWORD_GUARD`); a login is also refused while another one for the client is in flight (on any API instance), and at most 20 logins per client per hour. In this process: logins, CAPTCHA images and list fetches are limited per person in an org, per person across orgs, per client, and for the whole process with a budget per kind (CAPTCHA images never use up the logins); one step runs at a time per client. Budgets are spent only after a read-only check that the member may run the sync and the org has a tax code, so refused calls (a viewer, an org without a tax code) cost nobody's budget. The guard counts per Crove org: two orgs that declare the same tax code each have their own count, and an org that changes its tax code keeps its count across the change (stricter, never looser). The portal account is per tax code; counting across orgs would need a definer that reads every tenant's calls, and anyone can also try the portal directly, so the per-org count is accepted for now.
7. **Egress to one fixed origin.** The client talks only to `https://hoadondientu.gdt.gov.vn/api` through the egress guard (`guardedRequest`): public addresses only, the connection pinned to the checked address, one deadline per request (20 s), a byte cap per answer (200 KB for a CAPTCHA, 4 MB for a list page, 5 MB for an XML), no redirects, no cookies, no compression. The real portal is recognized by its parsed host name, exactly, and only over https; a configured URL with credentials, a query or a fragment is refused. Paging is bounded (40 pages per query and month, 20,000 rows), and each `fetchList` or `fetchXml` step has one deadline for all its requests (`TAX_PORTAL_STEP_SECONDS`, default 90, never past the session's expiry): a request gets at most the time left, the next request is not made past it or once the browser has gone (the request's abort signal), and the step stops resumably (`PORTAL_STEP_TIMEOUT`; an XML batch answers what it finished and the next call goes on). The XML plan reads only the list of the session's period. A 429, a 403 or an HTML page served with status 200 stops the sync at once. `TAX_PORTAL_URL` (operator configuration, not in the compose passthrough) points a test deployment at a fake portal: the API refuses to start with it unless `PUBLIC_URL` is local (`localhost` or a `.test` name), since the client's real password would go to that address; the end-to-end tests use it.
8. **Who may run it.** Owners, admins and members of the client's org, which is how the firm's accountants work across clients (a membership in each client org); viewers and non-members are refused by the commands. The org's tax code is the portal user name, read from the org, never typed; a list whose buyer is another company is refused as for an upload. The accountant confirms the client's consent before logging in, recorded in the login call's audit row.
9. **Off by default.** `TAX_PORTAL_SYNC=false` unless the deployment opts in, since it logs in to a government portal on a client's behalf (spike O1 and O2). With it on, the API refuses to start without the credential key. The screen shows the flow only when `/api/config` says `taxPortalSync`.

## Consequences

- The accountant keeps the page open while the XML downloads run (a few minutes for a busy month); closing it stops the sync, and the next sync goes on from the invoices still missing.
- A process restart between steps loses nothing but the session: the screen asks for a new login.
- The endpoints and shapes come from public tools, not from the live portal (see the integration page): the first real use is a supervised trial on a partner's account, with their consent, by a person. Nobody ran it against the real portal while building it.
- Requests come from the server's IP. The portal may block hosting outside Vietnam (spike section 2.1); the screen then says the portal blocks this server and points to the Excel import, which stays.

## Options considered

1. **Bounded steps with a sealed session held by the browser (chosen).** No new table, no secret at rest, works with several API instances.
2. **One background job with the sealed token in its payload.** The accountant could leave the page, but the envelope would sit in the job tables after the job ends, and a new table or job payload would hold a portal session server side. Rejected for v1.
3. **A sealed token in a new table, dropped by the job.** Same as 2 with a cleaner drop, but a new tenant table (RLS factories first) for a value that lives 20 minutes. Rejected for v1; revisit if the screen-driven flow proves too fragile.
4. **Keep the token in the API's memory only.** Breaks with more than one API instance. Rejected.
5. **Store the password (design B) or solve the CAPTCHA by software (design C).** Rejected by the owner (O3, and the project's rule).
