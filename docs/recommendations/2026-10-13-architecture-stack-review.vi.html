Crove OS · Đánh giá kỹ thuật

Kiến trúc và tech stack: có phải tốt nhất chưa?

Đánh giá lại plan Crove OS Kernel theo 4 tiêu chí: scale, tích hợp third-party, dev thêm tính năng dễ, hiện đại và được dev yêu thích. Ràng buộc duy nhất là PostgreSQL; mọi lớp khác đều được phép đổi.

Ngày 13/10/2026 Version, ngày phát hành, download: tra trực tiếp npm registry, GitHub API và docs chính thức trong ngày

Tóm lại: phần lõi backend của plan đã gần như là lựa chọn tốt nhất hiện có. Chỗ lệch rõ nhất là frontend: plan dùng Next.js nhưng chỉ dùng một phần nhỏ của nó: Server Actions không phải đường ghi ('use server' chỉ cho logout và đổi ngôn ngữ), use cache chỉ cho dữ liệu không thuộc tenant, RSC chỉ chặn đăng nhập và nạp org context, dữ liệu lấy phía client qua TanStack Query, tắt typedRoutes và tự viết route generator. Một SPA trên Vite 8 + TanStack Router làm đúng việc đó mà ít code tự viết hơn, build nhanh hơn, dễ tự host hơn. Next vẫn phổ biến hơn nhiều (67,7M download/tuần so với 11,6M của TanStack Start), nhưng theo State of JS 2025 mức hài lòng với Next đang giảm, còn TanStack Start là cái tên được dev tự điền vào nhiều nhất.

Về kiến trúc, có 2 bổ sung đáng làm ngay vì rẻ bây giờ nhưng đắt về sau: chuẩn bị chia tenant theo cell (nhiều DB) và vạch lộ trình nền tảng tích hợp (OAuth app, SDK, webhook outbound) thay vì dồn hết vào Phase 3.

Kiến trúc kỹ thuật của plan

Gọi đúng tên các pattern: modular monolith TypeScript, command-oriented (CQRS-lite) với một pipeline ghi duy nhất, contract-first + codegen, shared-schema multi-tenancy bằng Postgres RLS và context có chữ ký, transactional outbox + event-driven async, và policy engine coi AI agent là một actor có quyền hạn chế.

Đánh giá theo 4 tiêu chí

1. Scale

Đã tốt

  • API stateless, autoscale trên Cloud Run; worker pool scale độc lập.
  • Mọi bảng tenant có PK (org_id, id), không có UNIQUE(id) toàn cục, không join chéo org: về sau tách tenant sang DB khác (cell) là khả thi. Ngoại lệ là các bảng identity như user_account, tenant (thuộc control plane, xem đề xuất #5).
  • Đọc và ghi đã tách wrapper (withTenantReadTx), nên định tuyến query đọc sang read replica rất dễ.
  • Queue công bằng theo org; outbox lag > 30 giây thì tạm dừng job nền; quota và abuse limit theo org.
  • Audit partition theo năm; bảng nóng có TTL.
  • Số dư sổ cái có bảng period_balance (Phase 2a), chỉ definer ghi sổ được ghi và đối soát hằng đêm, nên báo cáo không phải SUM lại toàn bộ sổ.

Giới hạn

  • Một Postgres primary là trần ghi. Đủ cho hàng nghìn tenant SME (plan ước tính 5.000 tenant ≈ 1,5-3k USD hạ tầng/tháng, chưa tính LLM), không phải vô hạn.
  • Relay outbox chạy độc quyền trên 1 instance (advisory lock): đây là trần throughput event. Suy luận (chưa đo): đủ cho giai đoạn đầu; khi lớn cần chia relay theo hash(org_id).

Đề xuất

  • Làm cell-ready ngay (đề xuất #5). Read replica cho báo cáo khi cần.

2. Tích hợp third-party

Đã tốt

  • Một registry sinh ra 5 bề mặt: RPC nội bộ, REST/OpenAPI, MCP, AI tool, webhook event. Command mới tự có mặt ở mọi kênh mà nó khai báo.
  • Webhook vào gắn với binding: org suy ra từ binding, chữ ký verify trong API, xử lý async.
  • Connector chạy trong job có khai báo egress; ledger external_call cho idempotency và đối soát khi kết quả mơ hồ; credential được mã hóa envelope bằng key của deployment (Cloud: KMS), chỉ job khai báo egress đúng provider mới giải mã được.
  • Tên public đóng băng (CloudEvents com.crove.*), event có version và upcaster.

Lỗ hổng

  • Public API, webhook ra, MCP đều dồn vào Phase 3, tức khoảng 30 tuần sau mới có.
  • Chưa chốt Authorization Server (OAuth cho app bên thứ ba và MCP client) cho bản self-host; bản Cloud dựa vào DOS ID.
  • Chưa có SDK cho dev bên ngoài; chưa có chỗ cho app bên thứ ba gắn UI (cố ý chưa làm ở v1).

Đề xuất

  • Vạch lộ trình nền tảng tích hợp ngay (đề xuất #6).

3. Dev thêm tính năng

Đã tốt

  • Vertical slice: 1 module = 1 package + 1 schema + 1 role + manifest. Module mới = 1 file migration + pnpm g module.
  • Golden path: pnpm g command sinh contract, handler, test, i18n, route; 1 command = 1 file.
  • Ranh giới do máy kiểm tra (dependency-cruiser, DB role, lint), nên module này không làm vỡ module kia.
  • Vòng lặp local nhanh: theo số đo trong plan, db reset ≈ 38 giây, migration mới ≈ 2 giây, pgTAP < 1 giây.
  • Contract-first: UI, API, agent dùng cùng một type.

Rủi ro

  • Framework nội bộ khá lớn (define*, manifest, codegen), nên dev mới tốn công học.
  • Vài thứ đang tự viết mà thư viện đã có sẵn (route generator, AppLink, process engine).

Đề xuất

  • Chỉ tự viết những gì là lợi thế cạnh tranh (policy, proposal, ledger, audit); phần còn lại dùng thư viện (đề xuất #1, #2).

4. Hiện đại và DX

Đã có đủ các pattern năm 2026

  • Modular monolith, contract-first + codegen, type-safe từ DB tới UI.
  • RLS multi-tenancy, transactional outbox, durable process.
  • Policy-as-code cho AI, MCP-native, OpenTelemetry.
  • Toolchain viết bằng Rust/Go: tsgo (TS 7), oxlint; thêm Rolldown nếu sang Vite 8.

Cố ý không có (đúng giai đoạn)

  • Microservices, Kafka, k8s, GraphQL, local-first sync. Thêm vào lúc này chỉ tăng chi phí vận hành.

Đề xuất

  • Điểm trừ DX lớn nhất là frontend (đề xuất #1) và formatter còn beta (đề xuất #3).

Đề xuất thay đổi

  1. App shell: Vite 8 + React 19.3 + TanStack Router (SPA) Đổi · trước bootstrap PR #5 "web skeleton"
    • Giữ Next.js cho landing page (apps/web hiện tại, cần SEO). App sản phẩm đặt ở một app mới, build ra file tĩnh.
    • Bỏ được code tự viết:
      • Virtual file routes của TanStack Router dựng route tree từ manifest module mà vẫn có type, thay cho route generator và AppLink tự viết.
      • validateSearch bằng zod thay nuqs.
      • Loader tích hợp sẵn với TanStack Query, có prefetch khi hover.
    • Đơn giản hơn:
      • Tự host chỉ cần một thư mục file tĩnh.
      • CSP dạng hash dễ làm với index.html tĩnh, nên bỏ được spike A14.
      • Không còn bề mặt tấn công RSC: React có lỗ hổng RCE ở RSC ngày 03/12/2025, và Next có bản vá bảo mật ngoài lịch dự kiến ngày 14/10/2026.
    • Build nhanh: Vite 8 dùng Rolldown làm bundler duy nhất. Ví dụ Vite công bố: build của Linear giảm từ 46 giây xuống 6 giây.
    • Cái giá:
      • Chặn đăng nhập chuyển sang beforeLoad phía client; bảo mật thật vẫn nằm ở API.
      • app.crove.com và api.crove.com cùng site nên cookie vẫn dùng được.
    • Cập nhật kèm: ADR-0011; trong plan: §2 (các dòng Web, i18n/URL state, Shell auth), §3.1, §3.2, §3.4, §7.5 (Shell), §9, §15 (Frontend); bỏ spike A14.
    • Độ tin cậy: khoảng 75%. Nếu sau này cần SSR thì lên TanStack Start trên cùng router, không phải viết lại.
  2. Spike DBOS cho durable process Spike · trước Phase 2a, không nằm trên đường găng Phase 0
    • Phase 0-1 chưa có process chạy dài, nên giữ outbox + pg-boss như plan.
    • Trước khi viết process đầu tiên (đồng bộ ngân hàng, phát hành hóa đơn điện tử, chuỗi duyệt), spike 1 tuần so DBOS với process engine tự viết.
    • Pass khi đạt đủ:
      • Khôi phục workflow đúng trên Cloud Run worker pool mà không cần Conductor.
      • Chờ duyệt 7 ngày mà không chiếm slot queue.
      • Schema xuất được thành file SQL để commit.
      • Công bằng theo org.
    • Fail thì giữ plan.
  3. Formatter Chỉnh · Phase 0
    • Dùng Biome (formatter) hoặc Prettier cho tới khi oxfmt lên 1.0; vẫn giữ oxlint để lint.
    • Việc đổi lại sau này chỉ tốn một PR.
  4. oRPC v2 trước public API Chỉnh · trước Phase 3
    • /rpc nội bộ cứ chạy v1.
    • /v1 public chỉ mở trên oRPC v2, với error envelope do Crove tự định nghĩa (plan đã chọn RFC 9457), để bên thứ ba không gặp lần đổi format lỗi giữa v1 và v2.
    • MCP tool tự dựng từ contract qua MCP SDK chính thức, vì oRPC chưa có adapter MCP chính thức.
  5. Cell-ready ngay từ đầu Bổ sung · Phase 0, rẻ
    • @crove/db nhận org_id khi chọn connection pool, dù hiện tại mọi org trỏ về cùng một DB.
    • Tách rõ bảng "control plane" (identity, danh bạ tenant, staff, session) khỏi bảng dữ liệu tenant.
    • Kết quả: khi một DB đầy, chuyển nhóm tenant sang DB thứ hai (cell) mà không phải sửa code nghiệp vụ. Làm sau thì phải đụng mọi chỗ mở transaction.
  6. Lộ trình nền tảng tích hợp Bổ sung · mở rộng ADR-0019 (MCP grants) hoặc thêm ADR mới, trước Phase 3
    • Chốt Authorization Server cho OAuth app bên thứ ba và MCP client ở bản self-host. Ứng viên: Zitadel (AGPL, cùng license), Ory Hydra, Keycloak. Đăng ký client theo CIMD.
    • Webhook ra: tự làm trên outbox + Standard Webhooks; Svix OSS là phương án dự phòng.
    • SDK TS/Python sinh từ OpenAPI.
    • Cân nhắc kéo một phần read API + webhook ra sớm lên Phase 2, vì kế toán cần nối với ngân hàng, cổng thanh toán và công cụ BI.

Những gì dev có thể không thích

  • Nhiều luật và gate. G1-G6, tối đa 800 dòng mỗi PR, protected path... được thiết kế cho AI agent tự code. Dev người sẽ thấy nặng tay. Nếu sau này tuyển dev, nên ghi rõ phần nào là luật cứng (bảo mật, migration) và phần nào là hướng dẫn.
  • Phần Postgres khó. Role, definer, context có chữ ký, RLS: đúng về bảo mật nhưng khó debug. Plan bù bằng apply_tenant_conventions(), ma trận RLS sinh tự động và generator; dev bình thường gần như không phải đụng vào.
  • Framework nội bộ. Đây là cái giá của một "OS" có một đường ghi duy nhất. Cách giảm: mỗi thứ tự viết phải là lợi thế riêng của Crove; thứ gì thư viện đã làm tốt thì dùng thư viện (đề xuất #1, #2).
